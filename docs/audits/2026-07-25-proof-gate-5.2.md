### PR #115 — config repair hatch (threat model — Phase 1)

The PR adds `isThesmosConfigRepairTarget(root, filePath, brokenConfigPath)` in `claude-govern.ts`:
`normalize(resolve(root, filePath)) === normalize(resolve(root, '.thesmos/config.json'))` (or the
captured broken path). When config is a `ConfigLoadError`, only `Write`/`Edit` of that exact path is
allowed through; all other tools exit 2; scope check is skipped during repair; content scan (secrets/
dangerous) still runs via `CONFIG_DEFAULTS` fall-through.

**Threat surface identified (to be proven with tests before/while reimplementing):**

1. **Symlink / junction / alias** — `.thesmos/config.json` as a symlink to an outside file: the string
   compare passes and the Write follows the link, writing outside the repo. PR does no `realpath`.
   Needs explicit policy + tests.
2. **Case behavior** — macOS/Windows case-insensitive FS: `.thesmos/CONFIG.JSON` resolves to same
   inode but `===` fails (harmless false-negative) — while `.THESMOS/config.json` may match a different
   real file. Needs explicit policy.
3. **`..` traversal** — `resolve` collapses `..`, so `a/../.thesmos/config.json` normalizes to the
   canonical path (intended). But `../config.json` or `.thesmos/../config.json` must NOT match.
4. **Similar filenames** — `.thesmos/config.jsonx`, `.thesmos/config.json.bak`, `.thesmos/config-json`
   must NOT get the exception.
5. **Exception must not disable secret/dangerous-content scanning** — a malicious "repair" payload
   containing a live secret or another BLOCKER must still be rejected.
6. **Invalid project `package.json`** must not be misclassified as malformed Thesmos config.
7. **Redacted, machine-independent error output** — no absolute temp paths leaking.

Decision: reimplement with a hardened path helper (canonical compare + explicit symlink policy),
direct unit tests for the helper, and real built-guard integration tests (Write AND Edit).

## 2. Scanner correctness (Phase 2) — Issue #96

**STATUS: COMPLETE for fixture-side work. Harness green. 29 scanner gaps recorded, not fixed.**

### 2.1 Where it stands

- Fixture **completeness gate passes**: every BLOCKER-severity rule has a fixture.
- Harness: **419 tests / 219 fixtures — all passing**. Failures went **75 → 0**.
- Core workspace: **120 files / 4121 tests, 0 failures** (baseline this session: 4075 passing, 75 failing).
- Every one of the original 75 failures was resolved as either a **repaired fixture (45)** or a
  **recorded scanner gap (29)** plus **one harness limitation (1)**.
- The 29 gaps are *not suppressed*. They live in a self-healing `KNOWN_RULE_GAPS` ledger in the
  harness that asserts each gap **still exists**; repairing a rule fails its test and demands the
  entry be deleted. A gap can neither silently persist nor silently disappear.

### 2.2 Triage method (reproducible, evidence-based)

Rather than eyeball 75 fixtures, each failing fixture was re-run through `runReview()`:

1. re-run the positive fixture across **~80 candidate paths** → separates path-filter mistakes from
   real non-detection;
2. if it fires nowhere, re-run the rule against **its own `explain.badExample` and
   `explain.commonViolations`** → if a rule cannot detect the violation its own documentation
   describes, the rule is the defect, not the fixture;
3. if that also fires nowhere, re-run with **companion files** (`package.json` + lockfile) → catches
   multi-file correlation rules the single-file fixture model cannot express.

The triage tool reproduced the harness result exactly (65 = 65), so the classification below is
mechanical, not judgement.

**Three corrections were made to the triage tool itself during calibration** (each initially produced
a false `RULE_GAP`): missing `.git/COMMIT_EDITMSG` sentinel path; missing GraphQL schema/resolver
paths; and no multi-file probe (LIC_001). Spot-checking rules by hand is what surfaced all three —
the numbers below are post-correction.

### 2.3 Classification of the 65 remaining failures

|---|---|---|---|

| `BAD_FIXTURE` | 29 | Rule works (own `badExample` fires); fixture content is wrong | Fix fixture |

### 2.4 RULE_GAP — 29 BLOCKER rules that cannot detect their own documented violations

`GHA_001 SEC_021 SEC_029 AUTH_007 API_004 API_008 NEXT_038 DB_024 ZOD_028 ZOD_030 PRISMA_003 GQL_017
STATE_008 STATE_011 LOG_003 FORM_009 SLOP_001 DEP_001 AI_013 AI_016 AI_030 AI_038 AGNT_023 VIBE_033
LIC_009 GDPR_016 GDPR_020 EU_AI_001 EU_AI_002`

Each ships at BLOCKER severity while failing to fire on the violations its own `explain` block
documents. Confirmed root causes (read directly from source, not inferred):

- **GHA_001** — `RUN_RE = /^\s+run:\s*/m` requires `run:` preceded only by whitespace, so the ordinary
  YAML list-item form `- run: echo "${{ github.event.issue.body }}"` never fires. The rule's own unit
  tests only ever use `- name:` + indented `run:`, so the gap is invisible to them.
- **VERCEL_002** — `if (!isSourceFile(path) && !path.includes('.env')) continue;` skips `vercel.json`,
  the canonical place a `NEXT_PUBLIC_` secret is declared, for a rule named
  `vercel_server_secret_public_prefix`.

### 2.5 Separate defect — `return` where `continue` is required (scan abort)

[`rules/state.ts:434-435`](../../thesmos/rules/state.ts) — STATE_012's `detect()` uses
`return findings` inside the `for (const ... of changedFiles)` loop for both its `'use client'` guard
and its path guard. **One** client component or non-`app/` file therefore aborts scanning of every
remaining file in the diff, silently disabling a BLOCKER rule on realistic multi-file changes. This is
a correctness bug independent of the fixture, and is not caught by single-file unit tests.

### 2.6 Separate defect — rules that flag their own `goodExample`

Sweeping every BLOCKER rule's documented `goodExample` through its own `detect()`: **4 rules flag the
fix their own documentation recommends** — `SEC_009`, `SEC_033`, `DB_014`, `VIBE_026`. A user who
follows the suggestion is still blocked.

`SEC_033` is the clearest: `/href\s*=\s*\{(?!['"`]\/|['"`]https:\/\/|['"`]#)/` matches any non-literal
href, so its own `goodExample` (`href={safeUrl}`, a validated variable) fires. In practice it is a
"dynamic href" detector shipping at BLOCKER, not an XSS detector.

### 2.8 Fixture-registry defect

`AUTH_008` is **defined twice** — in both `blocker-fixtures-ai-agents.fixture.ts` and
`blocker-fixtures-ts-security.fixture.ts`. The harness runs both, so one rule silently consumes two
test slots and the duplicate masks disagreement between the two definitions. The completeness gate
cannot see this: it checks only for *presence*, never for *uniqueness*.

### 2.9 Additional defects found while repairing fixtures

- **Obfuscation-inside-the-string bug (root cause of ~6 dead fixtures).** Several fixtures wrote
  `"'use cli' + 'ent';"` — the concatenation is *inside* the string literal, so the fixture content
  was the literal text `'use cli' + 'ent';`, which matches nothing. Concatenation must happen at the
  TypeScript level (as `NODE_005` correctly did). Both affected modules now export a `USE_CLIENT`
  constant and document the trap.
- **GDPR_007 performs no PII check at all.** `detect()` fires on any line matching the
  Sentry/Datadog/LogRocket call shape, so a fully scrubbed `Sentry.captureException(e, { userId })`
  is flagged BLOCKER identically to one leaking `email`/`phone`. It *also* uses `return []` inside
  the `changedFiles` loop — the same scan-abort bug as STATE_012 (§2.5).
- **NODE_008 is inverted relative to its name.** `jwt_algorithm_none` fires when the `algorithms`
  option is **absent**, and does **not** fire on an explicit `algorithms: ['none']` — the actual
  alg=none attack.
- **SEC_022 covers only the middleware form.** `cors({ origin: '*' })` is detected;
  `res.setHeader('Access-Control-Allow-Origin', '*')` is not.
- **DORA_001 has no expressible negative.** It is gated on `existsSync('.thesmos/incident-classification.md')`,
  so under a fixture root the "policy present" case cannot be represented. Negative removed with a note.

### 2.10 Harness improvements landed

- `KNOWN_RULE_GAPS` self-healing ledger (§2.1) — asserts each recorded gap still exists.
- **Uniqueness gate** — fails on duplicate fixture definitions (catches §2.8, which the completeness
  gate structurally could not see).
- **Stale-gap gate** — fails if a `KNOWN_RULE_GAPS` entry names a rule that no longer exists, is no
  longer BLOCKER, or lost its fixture.
- **`companionFiles`** — multi-file fixture support; `LIC_001` (package.json + lockfile correlation)
  now genuinely exercises `detect()` instead of silently returning `[]`.

- Fix the two `return`-vs-`continue` scan-abort bugs (STATE_012 §2.5, GDPR_007 §2.9). These are
